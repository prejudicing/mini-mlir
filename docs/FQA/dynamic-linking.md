# 动态链接：为什么需要，以及为什么运行时找不到库

本文以 Linux 下的 C++ 程序为例，回答两个问题：

1. 为什么需要动态链接？
2. 构建时已经指定了库路径，为什么运行时还可能找不到库？

## 问题一：为什么需要动态链接？

假设程序调用一个库中的 `add()` 函数。头文件让编译器知道函数的声明，链接则负责把调用与函数实现连接起来。

使用静态库时，链接器将所需的目标代码纳入最终程序；使用动态库时，实现通常保留在独立的 `.so` 文件中，运行时由动态加载器加载并解析相关符号。

```text
静态链接：
程序 A：自身代码 + 所需的库代码
程序 B：自身代码 + 所需的库代码

动态链接：
程序 A ─┐
        ├── 使用独立的动态库
程序 B ─┘
```

动态链接主要有这些用途：

- **共享库文件**：多个程序使用同一份安装的库，减少重复存储；同一动态库的部分只读代码页也可以在进程之间共享。
- **独立更新**：如果接口和 ABI 保持兼容，可以更新库，而不必重新链接所有使用它的程序。ABI 包含调用约定、符号、数据布局等二进制层面的约定，仅函数名称相同并不足以保证兼容。
- **运行时扩展**：程序可以通过 `dlopen()` 等机制主动加载插件。这属于显式运行时加载，与程序启动时加载已记录的依赖有所区别。

代价是：运行环境必须提供兼容的动态库，并且加载器要能找到它。静态链接不需要在运行时再提供对应的 `.a` 文件，但更新其中的实现通常需要重新链接程序。一个程序也可以同时使用静态库和动态库。

## 问题二：指定过库路径，为什么运行时还可能找不到？

关键是区分两次查找：**构建时由链接器找库，运行时由动态加载器找库。**

假设库文件位于：

```text
/home/lzb/mylibs/libmathutils.so
```

构建命令：

```bash
g++ main.cpp -L/home/lzb/mylibs -lmathutils -o app
```

| 参数 | 含义 |
| --- | --- |
| `-L/home/lzb/mylibs` | 给链接器增加构建时的库搜索目录 |
| `-lmathutils` | 按库命名规则寻找 `libmathutils.so` 或 `libmathutils.a`；选择受链接模式和可用文件等影响 |
| `-o app` | 指定最终程序名称 |

**`-L` 的目录通常不会自动成为程序的运行时搜索路径。**

假设本次选择了动态库，程序一般会记录一个依赖名称，例如 `libmathutils.so.1`。这个名称通常取自库的 `SONAME`；具体记录取决于库的构建方式和链接输入，不保证总是这个例子中的名字。

```text
构建时：
链接器通过 -L 找到动态库
    ↓
生成 app，并记录所需的动态库名称等信息

运行时：
执行 ./app
    ↓
动态加载器读取依赖名称
    ↓
根据运行时搜索规则寻找对应的 .so 文件
```

因此，构建成功不代表运行环境一定能找到库。程序可能被安装或复制到另一台机器，构建时的路径也未必适合部署环境。

### 怎样提供运行时搜索路径？

以下是几种常见方式，不需要全部使用。

**方式一：仅为这次运行设置环境变量。**

```bash
LD_LIBRARY_PATH=/home/lzb/mylibs ./app
```

这会让本次运行的加载器在相应搜索环节考虑这个目录，适合个人实验和调试。

**方式二：构建时显式记录运行时搜索路径。**

```bash
g++ main.cpp \
  -L/home/lzb/mylibs -lmathutils \
  -Wl,-rpath,/home/lzb/mylibs \
  -o app
```

| 写法 | 解决的问题 |
| --- | --- |
| `-L...` | 链接时去哪里找库 |
| `-Wl,-rpath,...` | 将运行时搜索路径传给链接器，记录进生成程序 |

`-Wl,` 表示让 `g++` 将后面的选项传给链接器。现代 GNU 工具链通常生成 `RUNPATH` 条目；具体条目和搜索行为取决于工具链设置。

如果想让程序与库一起移动，还可以使用相对于可执行文件位置的路径，例如以下假定布局：

```text
package/
├── bin/app
└── lib/libmathutils.so
```

对应链接选项为：

```bash
-Wl,-rpath,'$ORIGIN/../lib'
```

这里的单引号用于阻止 Shell 提前展开 `$ORIGIN`；该标记由动态加载器按程序所在位置解释。

**方式三：配置系统库搜索目录。**

可以在 `/etc/ld.so.conf` 或 `/etc/ld.so.conf.d/` 下的配置文件中增加目录，再执行 `sudo ldconfig` 更新缓存。它适合系统级安装；个人实验通常使用前两种方式即可，无需修改系统配置。

以上方式提供的是目录。目录中还必须存在匹配依赖名称的库文件或有效符号链接，并且库本身及其依赖需要兼容。

### 怎样检查程序记录了什么？

在装有相应工具的 Linux 环境中，可以查看 ELF 动态信息：

```bash
readelf -d ./app
```

重点关注：

- `NEEDED`：程序直接依赖的动态库名称。
- `RUNPATH` 或 `RPATH`：程序中记录的运行时搜索路径；不一定存在。

这些命令中的 `app`、`mathutils` 和路径均为教学示例，需要替换为实际文件。

## 对应到本项目的 CMake

```cmake
target_link_libraries(app PRIVATE mathutils)
```

这条命令表达目标的链接依赖。最终是静态链接还是动态链接，取决于 `mathutils` 对应的目标或库文件。

CMake 在常见的动态库构建场景下也会处理构建目录中的 RPATH，因此不一定需要手动设置。但构建目录中的运行成功，不代表移动程序或安装后仍然成功；安装时的库位置和搜索路径仍需正确安排。

记住：**头文件提供声明，链接阶段连接实现；动态加载阶段在运行环境中找到并加载所需的库。**
